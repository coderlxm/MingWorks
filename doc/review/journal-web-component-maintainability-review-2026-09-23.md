## 结论与范围

本次保留 **一般 1 项、轻微 2 项，严重 0 项**。收益分别是：将富文本工具栏与编辑器业务分开维护、消除两处相同的正文编辑状态逻辑、合并两处相同的删除确认展示。它们是局部维护性改进，不表示现有功能不可用，也不要求立即重构。

依据是当前源码中的职责边界、重复实现和调用关系。重点重新阅读了富文本编辑器、记录卡片与详情、文章卡片、AI 页面、导航、媒体舞台、发布页和私有资产页。没有把文件长度作为问题证据，也没有把源码中的潜在开销写成已经发生的性能故障。

## 一般

### M1. 富文本工具栏可以独立维护

**源码依据**

- `apps/journal-web/src/components/article/RichTextEditor.vue:240`：工具栏独立成块，包含撤销、标题、文字格式、列表、表格、链接、对齐及图片操作；工具栏块结束于第 290 行。
- 同文件 `:77`：`run` 负责工具栏命令分发；`:111` 的 `promptLink` 负责链接命令输入；`:317` 起有工具栏专属样式及移动端规则。
- 同文件还持有编辑器实例、正文 model 同步、图片上传锚点、Markdown 应用与撤销边界。这些业务不属于按钮排列或格式命令展示。
- `TableControls.vue`、`ImageControls.vue` 已经使用“接收现有 editor 实例”的局部控件边界，可沿用项目现有组织方式。

**实际收益**

修改按钮分组、按钮名称、格式选中态或工具栏样式时，可以集中在一个工具栏组件内完成；正文同步、上传和 Markdown 处理留在编辑器容器。减少的是维护时需要同时理解的业务范围，不宣称提高输入速度或减少网络加载。

**合适的拆分范围**

提取一个富文本工具栏组件，集中放置工具栏模板、专属样式和普通格式命令。复用父组件创建的 editor；上传、素材插入等业务操作继续交给父组件处理。无需把每组按钮分别建成组件，也无需增加通用命令注册系统。

**行为边界与代价**

父组件继续拥有 editor 的创建和销毁、model 同步、图片上传锚点及 Markdown 应用。保留现有命令的 `focus()`、按钮禁用条件、选中态更新、移动端横向滚动，以及切换预览/Markdown 时的 `v-show` 保留行为。拆出后会增加一个组件接口；如果只是搬模板而仍让父组件维护全部工具栏细节，收益不足。

## 轻微

### M2. 卡片与详情重复维护相同的正文编辑状态

**源码依据**

| 重复内容 | 记录卡片 `EntryCard.vue` | 记录详情 `JournalDetailContent.vue` |
| --- | --- | --- |
| 本地 editing / draft | `:50`、`:54` | `:50`、`:54` |
| 正文变化后同步草稿并关闭编辑 | `:134` | `:80` |
| 取消后恢复原正文并关闭编辑 | `:139` | `:95` |
| 内容不同且非 busy 才能保存 | `:126` | `:70` |

完整目录为 `apps/journal-web/src/components/journal/`。两处编辑区分别从 `EntryCard.vue:252` 和 `JournalDetailContent.vue:192` 开始。

**实际收益**

将这套相同的草稿、取消、正文同步和可保存判断集中在一处后，维护这些规则由两处同步修改变成一处。当前没有证据表明两处行为已经不一致，因此等级为轻微。

**合适的拆分范围**

可提取一个仅服务这两个组件的正文编辑 composable，每个调用方拥有自己的状态实例，返回 editing、draft、canSave 和取消操作。父组件继续决定何时打开编辑，以及如何与删除确认、时间编辑互斥；保存仍通过原来的 `saveContent` 事件向外发送。

**行为边界与代价**

保留当前“收到新正文才同步草稿并关闭”的时机，不改成点击保存就提前关闭；取消后再次打开仍使用原正文。composable 随父组件创建，不随编辑区域的 `v-if` 重新创建。卡片的 6 行输入框、详情的 9 行输入框、不同样式和点击传播规则均保留。此次收益只来自逻辑去重，不要求统一两处 UI。

### M3. 两种卡片的删除确认区可以复用

**源码依据**

- `apps/journal-web/src/components/journal/EntryCard.vue:332` 与 `apps/journal-web/src/components/article/ArticleCardContent.vue:256`：均为内联 footer、提示文字、取消按钮、确认删除按钮和忙碌提示，禁用条件及事件结构一致。
- 两者的确认区样式分别位于 `EntryCard.vue:600`、`ArticleCardContent.vue:540`，背景、边框、间距、按钮高度等基本相同。
- `JournalDetailContent.vue:248` 虽也有删除确认，但确认文字为“确认永久删除”，且 `:507` 起的间距、边框、圆角等布局不同；不把它强行纳入本次复用。

**实际收益**

两种卡片的删除确认展示及公共样式由两份变成一份，调整提示区或忙碌展示时不必同步修改两份模板。重复块较小，因此只列为轻微整理项。

**合适的拆分范围**

提取卡片内联删除确认组件，接收提示文字和 busy，发出取消与确认事件。记录/文章及附件数量对应的提示文字、是否显示确认区、真正的删除请求仍由原调用方负责。

**行为边界与代价**

保持 footer 在卡片内的位置、原有按钮文案、busy 禁用以及事件传播，不改成弹框，不接管请求或删除状态。组件只服务这两个已有相同展示的入口，不扩展成通用确认系统。
