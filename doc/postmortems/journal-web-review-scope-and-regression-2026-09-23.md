# Journal Web 组件审查与弹框改动失败复盘

日期：2026-09-23  
依据：本次对话中的任务、修改经过、用户反馈与源码分析。本文记录本次教训，不是新的重构清单。

## 发生了什么

用户希望识别组件臃肿、维护成本和有实际收益的拆分机会。初次报告混入了交互改造及条件性优化建议。用户选中其中的游戏弹层条目后，代理将原有遮罩替换为原生 dialog，并改动了相关生命周期、表单关联及详情与编辑切换。

用户随后发现取消本地图片选择会关闭编辑弹框。事件处理器把文件输入控件冒泡的 cancel 当作弹框自身的取消事件。后续源码分析还发现原生模态顶层与挂在 body 下的消息提示存在层级冲突；这一项来自源码和浏览器规则推导，不是用户报告的实机现象。

相关代码最终全部撤回。旧报告被删除，新报告缩小为维护性建议，但后续讨论也明确：能够拆分、存在少量重复，不足以证明目前有值得专门处理的臃肿问题。本次没有交付业务或性能改善，产生了额外沟通与返工成本。

## 可以复用的教训

### 1. 先证明值得改，再讨论怎么改

原生弹框在特定场景下有焦点管理等技术价值，但本次没有建立这些能力与用户目标之间的收益关系。技术能力不能自动计入项目收益。

提出修改时，需要说明它减少了当前哪项使用或维护成本，以及为什么值得承担改动代价。无法说明时，保留原实现。运行正常不是不存在缺陷的证明，但应当提高替换已有机制所需的证据门槛。

### 2. 分开源码事实、问题判断与实施建议

“文件较长”“某段逻辑重复”“没有采用某种机制”属于源码事实；“已经难以维护或影响使用”是进一步判断；“换一种实现会更好”又是另一个判断。

每一步都需要自己的依据。不能从一种代码写法直接跳到严重程度和改造方案。维护性审查应允许没有需要修改的结论，也不必为了填满等级而增加条目。

### 3. 改动行数少，不代表影响范围小

把 div 换成 dialog 看似局部，却改变了事件、焦点、页面层级和其他控件的交互条件。本次漏项并非难以触达的外部输入，而是可以从代码和已知浏览器规则中推导出的联系。

修改基础交互机制前，应沿实际功能追踪打开、操作、取消、再次打开、提交反馈和关闭的连续路径。尤其要问：事件可能来自哪些子控件，现有提示显示在哪里，哪些组件会保留或销毁。只看替换位置本身不足以理解影响。

### 4. 功能行为应当是结构整理的约束

用户选择报告条目，并不免除报告作者判断条目是否符合原任务的责任。组件拆分应围绕独立职责或实际重复，保留既有交互、请求时机和状态归属。

若必须同时更换弹框、调整缓存、改变加载策略或增设提示，已经进入功能行为调整，不能借“整理代码”一起实施。

### 5. 质量成本不能转嫁给用户

本次由用户发现回归、描述现象，再由代理定位，形成了额外的操作和转述负担。修掉自己引入的错误不能计为原任务收益，写出更多报告也不能抵消返工成本。

交付结论必须与证据相匹配。需要额外环境信息时应指出具体缺口，并遵守授权边界；不能擅自操作浏览器，也不能因工具操作受限而把可由源码查明的遗漏归因于用户。

### 6. 交叉 review 的价值在于反驳，不在于累加意见

第二个审查者适合寻找误报、合理取舍、遗漏的既有行为及建议本身的代价。把两份问题清单合并，可能只是扩大工作量。

多个模型一致不是事实证明；结论仍需回到源码、实际需求和可观察结果。交叉审查是一种可选的质量手段，不意味着今后所有小改动都要启动多模型流程。

### 7. 纠错时也要保持判断稳定，避免迎合

本次代理从强调规范性收益，转向笼统认可“没有收益”，之后又重新区分技术价值与项目收益，造成额外困惑。这种立场摆动降低了结论可信度。

应始终区分：某技术具备什么能力、用户是否需要、此次实现是否正确。承认实施失败，不必否认技术在其他场景下的价值；技术有价值，也不能为此次不必要的改动辩护。

### 8. 用户观察：聚焦局部修改时，可能遗漏关联交互这一层条件

用户提出一种可能解释：模型聚焦于一个功能点的修改时，未能同时叠加并保持对子控件事件冒泡等关联交互的认识。这是用户从本次过程注意到的细节，应作为待研究的解释保留。

本次可观察到的表现是：代理围绕“换成原生弹框”安排打开和关闭，却没有同时推演“文件输入也会发出 cancel，并冒泡到外层处理器”。分别能够解释 dialog 和事件冒泡，不代表在实际修改中已经将这些知识组合起来应用。同样，弹框层级的变化也没有与现有消息提示的挂载位置一起考虑。

这一观察提示，可靠修改需要持续保留局部目标与周边约束，不能只判断新写的一段代码是否单独合理。但当前证据只能支持“关联条件在实施分析中被遗漏”，不能据此确认是模型内部注意力机制的缺陷，也不能断言模型永远无法同时处理这些条件。

## 本次不能推出的结论

- 不能据此确认底层模型发生了降级，或判断某个具体型号的普遍能力。
- 不能证明 AI 完全无法审查已有代码，也不能保证换一个模型就不会重复错误。
- 不能证明项目完全没有维护问题；当前只能说，没有足够证据支持大规模重构。
- 不能把使用者降低预期当作解决方案。需求清楚时，保住原有正常行为仍是合理要求。

## 后续衡量标准

评价一次协作，应计算实现收益、用户介入时间、解释与审查成本、返工和回归，而不只看代码生成速度或报告条数。

对本项目这类维护任务，理想结果可以是：确认主要结构已经合适，保留正常实现，只在有明确收益和充分依据时实施局部整理。没有值得改的地方时，及时结束审查也是有效交付。
