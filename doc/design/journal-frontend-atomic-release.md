# Journal 前端整版切换建议

## 推荐改进

每次前端发布保留独立、完整的构建目录，准备完成后一次切换 `current` 链接。Fastify 只从 `current` 提供静态文件。已打开的页面发现线上版本变化后提示用户，由用户确认刷新。

这取代当前“把资源追加到在线目录、分别替换两个 HTML”的更新方式。后端仍独立发布，继续使用已有 GitHub Actions、上传入口、Fastify 和 Docker 挂载，不新增服务或依赖。

本文件为本轮实施依据，具体线上版本以部署结果为准。

## 目录与访问模型

```text
/opt/journal/web/                 固定挂载目录
  releases/
    <提交 A>/                    A 的完整静态产物
    <提交 B>/                    B 的完整静态产物
  current -> releases/<提交 B>   唯一在线版本
  retired/<提交 A>              文件修改时间记录 A 的退役时间
```

继续把 `/opt/journal/web` 只读挂载到容器 `/web`，将 `JOURNAL_WEB_ROOT` 改为 `/web/current`。链接使用相对路径，目标也位于挂载目录内部。

每个版本目录只包含该次构建实际产出的文件；不合并其他版本的资源，也不在已启用的版本目录中覆盖文件。两个 HTML 入口、JS、CSS、头像与图标通过同一个 `current` 指向同时切换。

旧版本目录可以存在于磁盘上，但不是对外静态根目录。访问缺失资源时正常返回错误，不向旧目录查找文件。

## 发布主路径

1. 沿用当前 CI 生成并上传完整前端包。
2. 在固定挂载目录内部的新临时目录解压，准备好全部文件及可读权限。
3. 将完整目录落到 `releases/<本次提交>`；在线目录始终不参与解压或覆盖。同一提交重复发布也不修改正在使用的版本目录。
4. 若本次同时发布后端，先按现有流程完成后端更新，仍需兼容切换前正在使用的前端。
5. 创建指向新版本的临时链接，再通过同一文件系统内的重命名替换 `current`。这是整版前端的唯一激活点。
6. 更新前端提交记录、清理本次上传包及过期的完整版本目录。

同一文件系统内重命名可以原子替换既有链接，避免出现先删除入口、再创建入口的空档。[Linux rename 文档](https://man7.org/linux/man-pages/man2/rename.2.html)

容器挂载固定父目录，链接切换发生在挂载内部；不把宿主机的 `current` 链接本身作为挂载源，也不替换挂载目录本身。Docker bind mount 的基本行为见 [Docker 文档](https://docs.docker.com/engine/storage/bind-mounts/)；上述目录布局是结合当前挂载方式的设计选择。

## 当前代码支持与确定性

本地安装版本为 `@fastify/static 10.1.4`。当前动态静态路由使用配置中的根路径；本地源码 `normalizeRoot` 保留根路径字符串，发送文件时使用该路径。Journal 的配置处理也使用路径规范化，没有把符号链接永久解析成某个提交目录。

因此，基于当前源码，静态根设为 `/web/current` 可以沿用动态路由，前端日常切换无需替换后端容器。这是源码依据与设计判断，不能将它描述成已经在线运行的新行为。

## 旧页面的边界

整版切换保证在线文件目录对应一个完整版本，不能把浏览器里已经执行的旧 JS 同时换成新 JS，也不能让一次页面加载的多个 HTTP 请求整体成为原子事务。

发布前打开的标签页，如果发布后才请求已经不在当前版本中的延迟模块，仍可能加载失败，需要刷新页面。暂时把旧目录留在磁盘上不会改变这一点，因为请求只访问 `current`。相关机制见 [Vite 官方说明](https://vite.dev/guide/build.html#load-error-handling)。

用户已经明确接受刷新页面。本方案通过下述新版本提示帮助用户主动刷新，继续保持单版本访问模型。

## 新版本提示与确认刷新

### 版本标识与发布一致性

前端 CI 使用本次提交 SHA 作为版本标识，通过 `VITE_JOURNAL_WEB_VERSION` 注入客户端，同时在完整产物中写入 `version.json`，内容为同一个版本标识，例如 `{ "version": "<提交 SHA>" }`。

客户端比较的是**当前正在执行的代码所属版本**与线上版本，不能把页面打开后第一次请求到的版本当作自身版本，否则旧代码可能错误地把刚发布的新版本当作基线。Vite 支持在构建时静态替换 `VITE_` 环境变量，见 [官方说明](https://vite.dev/guide/env-and-mode.html)。

`version.json` 与两个 HTML、所有资源处于同一个完整版本目录，随 `current` 一次切换。版本查询不读取后端镜像提交，也不依赖更新提交标记文件的先后顺序；后端单独发布不会触发前端更新提示。

Fastify 增加 `/version.json` 的明确静态文件路由，从配置的当前静态根读取文件，并设置 `Cache-Control: no-store`。浏览器查询也使用 `cache: 'no-store'`，避免缓存让版本变化迟迟无法被发现。[Fetch 缓存说明](https://developer.mozilla.org/en-US/docs/Web/API/Request/cache)

### 检测时机

主站 `App.vue` 与独立投稿页 `ContributionApp.vue` 共用一个小型版本检测 composable，各自在常驻根组件挂载期间运行：

- 页面进入时请求一次。
- 页面可见期间每 60 秒请求一次。
- 从后台恢复可见时立即请求一次；后台期间暂停周期请求。
- 同一时间只允许一个版本请求，根组件卸载时释放计时器和事件监听。

本地已安装 `@vueuse/core 15.0.0`，公开导出包含 `useIntervalFn` 和 `useEventListener`，可以复用它们管理周期和生命周期，见 [VueUse 文档](https://vueuse.org/shared/useintervalfn/)。无需新增依赖、服务端推送连接或全局状态管理模块；事件与生命周期直接驱动逻辑。

实现复用已安装的 `zod 4.6.5` 校验版本文件与编译版本，版本限定为 40 位小写提交 SHA。组件卸载主动取消在途查询，这是正常生命周期结束；查询失败仍按下面的规则暴露并停止检测。

机制仅在发布产物中运行，本地开发入口不参与线上版本比对。请求失败或版本文件内容不正确时停止周期检测并通过现有错误提示暴露问题，不把失败当作“没有更新”，不自动重试。

### 用户交互

发现版本不同后，在页面上显示一个轻量全局提示：“网站已更新，有新版本可用。”提供“立即刷新”和“稍后”两个操作。检测过程保留页面框架、路由、列表、编辑内容和滚动位置，不重新加载业务数据。

点击“立即刷新”后，复用项目已有的浏览器确认交互，提示：“刷新后将使用最新版本。未保存的内容会丢失，正在进行的上传或提交会中断，请先完成操作。确定刷新？”

- 点击确定：调用 `window.location.reload()`，重新加载当前完整地址，保留路径、查询参数和 hash；投稿链接中的 token 不会因拼接新地址而丢失。
- 取消确认：保留新版本提示和当前页面，用户可以完成操作后再次点击。
- 点击“稍后”：收起本次目标版本的提示，同一页面会话内不因每次周期请求反复提示同一版本；用户仍可手动刷新。
- 后续发现另一个不同版本时可以再次提示；线上版本重新与本地代码一致时移除提示。

刷新操作的语义见 [Location.reload 文档](https://developer.mozilla.org/en-US/docs/Web/API/Location/reload)。新版本提示组件和检测逻辑直接随主站、投稿页入口加载，不采用按需加载，避免旧页面在发布后才请求提示组件自身的旧模块。

当前文章编辑页和投稿表单已有 `beforeunload` 离开提醒，继续保留；如果用户在浏览器的既有离开提醒中取消刷新，新版本提示也继续保留。刷新确认统一说明未保存内容与进行中操作的影响，不额外建立全站脏数据登记系统，不自动保存、自动刷新或吞掉模块加载错误。

### 能力边界

这是用户主动确认的版本更新机制，不是旧资源兼容机制。它会在周期查询或页面恢复可见时发现更新，不能保证每个跨发布的旧模块请求之前都已经提示，也不能恢复已经发生的旧模块加载失败。用户确认刷新后，页面重新加载当前完整版本。

组件职责保持简单：`useFrontendUpdate.ts` 负责版本比对、提示状态和刷新确认；`AppUpdateNotice.vue` 只负责提示内容和两个按钮，通过 props 接收显示状态，通过事件表达刷新或稍后操作。两个根组件只负责接入。

## 保留与清理

沿用用户已确定的 7 天期限，但保留对象改成独立的完整旧版本目录，而不是在线目录里的历史资源。

- 当前版本始终保留。
- 旧版本从被替换时起保留 7 天，只作为完整发布产物留存，不承担旧浏览器页面的资源服务。
- 成功发布时删除超过期限的旧版本整目录；不再维护逐文件资源清单，不永久额外保留上一版前端。
- 后端仍保留当前与上一版镜像，沿用现有清理逻辑。

若最终决定前端无需历史产物，旧目录也可在切换完成后清理；这个保留策略选择不影响整版切换结构。

## 首次迁移与备份恢复

首次迁移使用 CI 本次产出的干净完整目录，不把当前已经追加过的在线目录当成新版本产物。先准备新目录和 `current`，再发布静态根改为 `/web/current` 的后端；切换成功后移除固定目录根部的旧布局文件。固定挂载目录保持不变。

服务器现有发布脚本会在后端启动之后才更新自身，不能执行这次迁移顺序。因此首次发布前先安装本轮新发布脚本，再沿用既有 Actions 发布；首次迁移必须同时发布前后端。后续整版切换由该脚本直接完成。

首次上线前已打开的页面还没有版本检测代码，需要手动刷新一次。载入本轮版本后，后续发布才会产生新版本提示。

备份先读取 `current` 指向的具体版本，再从这个固定版本目录复制完整前端产物，避免复制过程中跟随发生切换的链接。前端提交应由同一个版本指向确定；提交标记继续用于查看。

恢复时将备份中的完整产物放入对应提交目录，建立 `current`，再启动后端。日常备份只需当前前端版本，不必附带服务器上保留的全部旧目录。

备份格式更新为 v3，以区分旧目录布局与整版布局。当前恢复脚本仅接受 v3；已有 v2 包应使用与其对应的旧版恢复脚本，不能交给本轮脚本恢复。
