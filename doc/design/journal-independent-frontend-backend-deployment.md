# Journal 前后端独立发布方案

## 目标

Journal 前端源码变更只生成、上传和更新前端静态文件；后端源码变更只生成、上传和替换后端镜像。前端发布不重建或重启后端容器。两端同时变更时，同一次 workflow 分别发布两个产物。

沿用 main 推送触发 GitHub Actions、SSH 上传到 rndc02、现有发布脚本激活的路径。

## 当前证据

- 对应 [workflow 36730378917](https://github.com/coderlxm/MingWorks/actions/runs/36730378917/job/109938163473) 已成功。日志仍包含前端构建、向 runtime 镜像复制前端 dist、导出和上传完整镜像，以及重新创建 `notinews-journal` 容器。
- `.github/workflows/deploy.yml` 将前端、后端和部署文件统一归入 `journal`，触发同一个完整镜像发布步骤。
- `deploy/journal/Dockerfile` 的 runtime 同时包含后端源码和前端 dist。
- rndc02 实际运行的 Compose 只挂载 `/opt/journal/data`；前端文件来自镜像。
- Fastify 既提供 API，也提供静态文件、首页、投稿入口和 Vue 页面导航。OpenResty 已代理这些请求。

因此，拆分必须同时处理触发范围、产物、服务器文件位置和静态文件路由。

## 推荐结构

前端作为独立静态文件包发布到 `/opt/journal/web`，该固定目录只读挂载到 Journal 容器。`JOURNAL_WEB_ROOT` 指向挂载目录。

后端镜像移除前端构建阶段及 dist 的复制，只包含后端执行所需的源码、依赖和系统工具。Fastify 继续从外部目录提供页面和静态文件。

这样可以直接利用已有服务和代理，不需要增加静态网站容器或重新分配域名、端口。

## workflow 调整

保留 `journal` job，新增 `journal_web`、`journal_backend` 两个变更输出。job 内按输出执行对应的构建、打包、上传和激活步骤，并在步骤名称与通知中明确发布的是前端还是后端。

选择保留 job 是为了沿用 Bot 当前依赖 Journal 发布结果的关系，避免为本次拆分另建汇总任务。

| 变更输入 | 发布范围 |
| --- | --- |
| `apps/journal-web/**` | 前端 |
| `src/journal-server/**` | 后端 |
| `src/ai/models.ts`、`src/fetchers/qweatherCurrent.ts` | 后端；它们实际进入后端镜像 |
| `src/shared/**` | 前端与后端；两端都引用共享协议与内容处理逻辑 |
| 后端 Dockerfile、Compose、后端运行配置 | 后端 |
| 发布脚本、workflow 中 Journal 发布流程 | 涉及发布机制，首次调整时两端一起发布 |
| Journal 备份及恢复脚本 | 后端发布附带安装相应主机文件 |
| 根清单中的 Journal 前端脚本 | 前端 |
| 根清单中的 Journal 后端脚本 | 后端 |
| 根依赖、根 importer、共同工具链配置变更 | 前端与后端 |

当前前后端共同使用根 `package.json` 和根锁文件 importer，因此共同依赖变更仍是两端共同输入。本次先拆开源码发布和部署产物，不再扩展成依赖工作区重组。

手动 workflow 将 Journal 的选择拆成前端与后端两个开关。其他应用保留现有触发规则。

## 静态文件更新必须处理的细节

### 新资源不依赖后端重启

当前 `@fastify/static` 安装版本为 `10.1.4`，注册时使用 `wildcard: false`。本地源码显示该模式在启动时枚举文件并建立路由；[官方说明](https://github.com/fastify/fastify-static#wildcard)也明确该模式不会提供之后新增的文件。

前端每次生成新的哈希文件名，所以仅挂载目录仍不足以独立发布。需要改为动态匹配静态文件的路由模式，让新资源能在已有后端进程中被读取。既有 API、媒体、首页、投稿和页面导航处理继续承担各自的请求。

### 更新固定目录中的文件

`/opt/journal/web` 本身保持为同一个挂载目录，发布更新目录中的文件。不要通过替换整个宿主机目录来激活，因为容器挂载可能继续引用旧目录。

先将新静态资源写入最终位置，再替换入口 HTML。入口先写临时文件，完成后在同一文件系统内重命名，避免读取到只写了一部分的页面。

`assets` 中内容哈希命名的资源采用追加发布，保留先前发布的资源，使已经打开的页面仍能加载其引用的延迟模块。首页和投稿入口必须在各自引用的资源写入完成后更新。

### 首次启动依赖前端目录

`siteProfileService.initialize` 在尚未创建站点资料时，从 `JOURNAL_WEB_ROOT` 读取默认头像。独立后端首次运行前，前端目录必须完整且容器用户可读，包含默认头像及两个 HTML 入口。

## 发布与首次切换

### 后续日常发布

前端发布：生成静态产物 → 上传静态文件包 → 更新挂载目录中的资源和页面入口 → 更新前端提交标记。整个过程不加载镜像、不执行容器替换。

后端发布：生成后端镜像 → 上传镜像及所需主机文件 → 使用现有 Compose 替换后端容器 → 更新后端提交标记。前端目录保持当前发布内容。

两端同时发布时，先准备前端资源，再更新后端，最后切换前端入口。涉及接口变化的同批修改，应使后端能够服务切换期间仍打开的原前端页面；独立发布不意味着接口可以无序变更。

继续使用已有 `journal-deploy-release` 特权入口，按前端、后端及同时发布区分操作。前端分支仅管理静态产物；后端分支沿用当前镜像激活操作。

### 首次切换

首次需要发布两端，并完成一次服务器发布入口更新：准备完整前端目录、安装新版发布脚本、安装包含只读挂载的 Compose、再启动拆分后的后端镜像。这次容器替换是接入外部静态目录所必需的。

当前服务器脚本只接受原来的整包发布参数，不能直接假定它已支持新参数。实施时应把首次脚本安装作为明确的切换步骤，避免新 workflow 先调用旧脚本。

本轮仅形成方案，尚未进入服务器修改或正式发布阶段。

## 提交标记与现有备份恢复

保留 `.deploy-commit` 记录后端镜像提交；新增 `.web-deploy-commit` 记录前端提交。前端更新不能覆盖后端镜像标记。

现有备份以一个提交代表整个 Journal，恢复脚本也按一个提交重新生成整包镜像。拆分后必须同步调整：备份记录两端提交并包含当前前端静态产物；恢复时按后端提交恢复后端、恢复前端目录，再启动带挂载的容器。否则一次前端更新后，备份中的单个提交不能准确代表运行版本。

## 最小实施文件范围

| 文件 | 必要调整 |
| --- | --- |
| `.github/workflows/deploy.yml` | 前后端变更输出、条件步骤、各自产物及手动开关 |
| `deploy/journal/Dockerfile` | 移除前端构建和 dist 复制 |
| `deploy/journal/compose.yaml` | 固定目录只读挂载及静态根目录 |
| `deploy/journal/deploy-release` | 按发布范围激活产物、分别记录提交 |
| `src/journal-server/server.ts` | 静态资源动态路由 |
| `scripts/journal-backup` | 两端版本和前端产物进入备份 |
| `scripts/restore-journal` | 恢复独立前端目录及对应后端镜像 |

不需要新增运行时依赖。现有根依赖安装方式可以继续使用，后端当前复制的必要源码及系统工具也必须保留。

## 预期结果

下一次仅修改发布时间字段样式时，workflow 只生成并上传前端文件包，后端容器及镜像提交保持原版本。仅修改 Journal 后端业务时，只更新后端镜像，前端无需重新生成或上传。

该结果是方案目标；现有线上服务仍运行整包部署方式。
