# Journal 发布产物保留与清理建议

## 建议结论

后端保持现有“当前版本 + 上一版本”的镜像保留方式。前端建议在下一批发布机制调整中增加“当前版本 + 上一版本 + 被替换后 7 天内的版本”资源保留规则，结束旧哈希资源无限累积的状态。

当前前端目录约 3 MB，没有立即手工删除的必要。清理应随前端成功发布执行，复用现有发布脚本，不增加定时任务、服务或运行时依赖。本文件只提出建议，不改变已部署行为。

## 已有证据

2026-10-01 的服务器读取结果：

- `/var/lib/journal-deploy/incoming` 为空，发布临时目录已经清理。
- `/opt/journal/web` 约 3 MB。
- Journal 有当前提交和上一提交两个带提交标签的镜像。

当前 `deploy/journal/deploy-release` 在成功路径中删除前端上传包、后端镜像上传包及主机文件包；退出时移除解压临时目录。后端发布完成后删除更早的提交标签镜像。前端更新则保留既有 `assets` 文件，没有历史资源清理规则。

删除旧资源会影响已经打开的页面：旧页面可能稍后才加载对应的动态模块。这一机制与 [Vite 官方说明](https://vite.dev/guide/build.html#load-error-handling)一致，因此不能在新版本发布时直接清空 `assets`。

## 前端资源规则

### 保留范围

以下版本所包含的资源均保留：

1. 当前成功发布的版本。
2. 上一次成功发布的版本。
3. 被新版本替换至今不足 7 天的其他版本。

7 天是用户确定的保留窗口，不是库的技术要求。它给长期打开的页面留出使用窗口，也使历史资源最终能够清理。超过保留窗口的旧页面仍可能因旧模块已删除而加载失败，刷新后使用当前版本；任何有限期限都不能保证永久打开的旧页面一直可用。

时间从版本**被替换时**计算。不能按文件修改时间或版本初次发布时间判断：一个版本可能连续在线几个月，刚被替换时仍需要完整保留。

### 最小实现方式

仅增加版本资源清单及替换时间记录，放在 `/opt/journal/web-releases`，位于对外静态目录之外。无需按版本复制整套前端文件。

每次前端发布的主路径：

1. 从本次静态产物记录完整的 `assets` 文件清单，包含延迟模块、样式、图片等，不能仅提取 HTML 中直接引用的文件。
2. 沿用现有顺序写入资源、完成必要的后端切换、原子替换 HTML 入口。
3. 在前端切换成功后记录新版本，并为刚被替换的版本记录替换时间。
4. 合并所有应保留版本的资源清单，只删除 `/opt/journal/web/assets` 中不在合并清单里的文件，再移除过期版本记录。

相同哈希资源可能被多个版本共同使用；必须先合并清单再删除，不能逐个过期版本删除其全部文件。重复发布同一个提交时保留已有版本记录，不将当前提交标记为已被替换。

首次接入资源清单时，把现存 `assets` 整体记录为当前版本的基线，保留已有页面使用的资源；后续新版本使用本次产物的准确清单，旧基线按上述规则自然退出。

清理仅涉及 `assets` 和版本记录，保留固定挂载目录本身。HTML、头像、图标等非哈希入口或公共文件继续由发布流程更新。后端单独发布不触发前端资源清理。

## 后端镜像规则

沿用现有保留方式，不再增加更多镜像版本。仅处理 Journal 镜像仓库中以提交 SHA 命名的版本；不执行面向整台服务器的 Docker 清理，以免影响其他应用。

现有镜像依赖仍共同来自根清单，本次不扩展为依赖拆分或镜像瘦身。那属于另一项优化，需要以实际依赖使用为依据单独判断。

## 上传包与备份

成功发布时的上传包、解压目录清理已经存在，保持即可。失败后尚未消费的上传包可能留下，待该次问题处理结束再删除对应文件，不按固定期限批量删除正在上传或仍需定位问题的产物。

当前备份会包含整个前端目录。引入资源清理后，备份自然只包含仍保留的资源，继续保留前后端提交标记；恢复时同时还原版本资源清单和替换时间记录，后续发布才能延续正确的清理规则。

若实施，必要改动集中在 `deploy/journal/deploy-release`、`scripts/journal-backup` 和 `scripts/restore-journal`，无需改动前端业务或后端业务代码。
