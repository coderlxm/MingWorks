# 个人知识助手流式输出方案

日期：2026-09-12。阶段：官方 API 调研与实现设计。本次只产出方案。

## 1. 目标与推荐选型

让回答随模型生成逐步出现在当前消息中，具备类似 ChatGPT 的打字观感；查阅记录时显示真实进度，生成过程中允许停止，完成后继续沿用来源查看和私有文章保存。

推荐链路：

```text
DeepSeek 流式响应
  → Journal 服务端读取增量、执行工具、记录最终结果
  → 同一次 POST 响应通过 SSE 发送业务事件
  → 浏览器 fetch 读取事件流
  → Pinia 更新对应会话中的消息
  → Vue 逐步显示文本
```

继续使用当前 `deepseek-v4-pro`、关闭思考模式、最多五次模型调用、每次输出上限 2,048 token。此次改变数据传输和呈现方式，不为实现动画增加一次模型生成。

新增两个直接依赖：服务端 `eventsource-encoder`、浏览器端 `eventsource-parser`。复用现有 SDK、Fastify、Pinia、Vue 与 Markdown 渲染。

## 2. DeepSeek 官方接口结论

当前官方 Chat Completions API 支持以下行为：

| 项目 | 官方定义及本项目用途 |
| --- | --- |
| `stream: true` | 响应改为 SSE 消息增量，协议终止标志为 `data: [DONE]` |
| `choices[].delta.content` | 增量正文；每次可能包含多个字符，不保证一个事件对应一个汉字 |
| `delta.tool_calls` | 工具调用也会分片，按 `index` 归并；名称和 ID 出现在起始片段，后续追加参数字符串 |
| `finish_reason` | `stop` 表示正常结束；`tool_calls` 表示进入工具执行；长度限制、过滤、资源中断等不能算回答完成 |
| `stream_options.include_usage` | 与流式请求配套；当前文档说明最终块携带整次请求的 token 用量 |

依据：[DeepSeek 官方 Chat Completions API](https://api-docs.deepseek.com/zh-cn/api/create-chat-completion/)、[官方 Tool Calls 指南](https://api-docs.deepseek.com/zh-cn/guides/tool_calls/)。

实现应按当前 DeepSeek 定义读取结束原因和用量，不能把其他服务商的分片示例直接视作 DeepSeek 的返回约定。正文暂时为空也可能只是角色或工具信息片段，只有一轮流结束后的完整结果才能决定是否发生空回答错误。

本地 `openai` 包版本为 `7.5.0`，其公开类型提供流式 `create` 重载，返回可异步迭代的 `Stream<ChatCompletionChunk>`；请求选项支持 `AbortSignal`。因此可保留现有兼容客户端与 DeepSeek 地址，新增流式调用路径。以上来自本地包源码，不是对线上响应的声明。

## 3. 库的选择

| 能力 | 选择 | 引入情况与原因 |
| --- | --- | --- |
| 调用 DeepSeek | 现有 `openai@7.5.0` | 已安装，负责上游流式响应解析与请求取消 |
| 输出 SSE | `eventsource-encoder@1.0.2` | 新增服务端依赖，使用 `encode` 编码事件，交给 Fastify 原生流响应发送 |
| 读取 SSE | `eventsource-parser@4.1.0` | 新增前端依赖，使用 `eventsource-parser/stream`，处理事件跨网络分片和多行数据 |
| HTTP 与取消 | 原生 `fetch`、`TextDecoderStream`、`AbortController` | 无新增包，沿用 POST 和站主 Cookie |
| 界面增量更新 | 现有 Vue、Pinia、`marked` | 无新增包，沿用现有消息展示与 HTML 输出约束 |

上述两个新包的版本已由 npm registry 元数据核对。Parser 的 Node 要求为 `>=22.12`，Encoder 为 `>=18`；两者均未声明运行时依赖。项目声明与 Journal 镜像均使用 Node 24。当前项目依赖声明及锁文件没有这两个包，本次也不安装；实际接入时应同步确认安装后的导出、类型和锁文件解析结果。

包资料：[Parser 文档](https://github.com/rexxars/eventsource-parser)、[Parser 发布元数据](https://registry.npmjs.org/eventsource-parser/4.1.0)、[Encoder 文档](https://github.com/rexxars/eventsource-encoder)、[Encoder 发布元数据](https://registry.npmjs.org/eventsource-encoder/1.0.2)。

选择 Parser 是因为网络分片不等于 SSE 事件边界；不能自行按换行拆包并假设每段就是完整 JSON。选择 Encoder 则让协议转义与事件编码交给现成库。

Fastify 已有流响应能力，可将业务异步生成器通过 Node 原生 `Readable.from` 转成字节流，再由 `reply.send` 发送；无需另加 SSE 服务端插件。[Fastify 官方流响应说明](https://fastify.dev/docs/latest/Reference/Reply/#streams)

原生 EventSource 的接口不提供本需求需要的 POST 请求体控制，且具有自动重连行为，因此采用 fetch 消费 SSE。此次不引入 WebSocket、AI SDK、LangChain 或打字动画组件。[EventSource 接口](https://developer.mozilla.org/en-US/docs/Web/API/EventSource)

## 4. Agent 多轮调用如何流式化

### 4.1 每一轮都使用流式调用

不能只把现有循环的第五次调用改成流式：模型通常会提前结束查阅，答案很可能在第二、第三轮就已经生成。

推荐保留现有循环，将每一轮模型请求都改为流式，累计该轮正文、工具调用和结束原因：

1. 开始一轮时发送轮次标识。
2. 收到正文增量立即转发给浏览器，并在服务端同步累计该轮文本。
3. 工具参数仅在服务端按工具 `index` 组装，整轮结束后才解析 JSON，并沿用现有 Zod 业务参数约束。
4. 工具轮结束后执行搜索或读取，发出真实的查阅状态，将工具结果放回模型上下文，进入下一轮。
5. 正常文本轮结束后，保存最终正文和真实来源，再发送业务完成事件。
6. 第五轮继续设置 `tool_choice: 'none'`；工具调用次数与错误处理规则沿用当前实现。

任何传输边界都不承担工具执行触发条件：半个 JSON、尚未结束的工具参数不能执行。

### 4.2 正文与查阅过程的区分

`tool_choice: auto` 下，不能在第一段文本到达时就认定这一定是最终答案。模型可能先写一句说明，再提出工具调用。

为避免先显示整段答案、随后突然清空重写，每一轮文本在同一助手消息内拥有稳定的 `roundId` 和独立文本块。工具轮产生的说明保留为“查阅过程”；最后正常结束那一轮才是最终正文，供后续追问和文章保存使用。已出现的文字不因为新一轮开始而被删除。

系统提示约定“需要调用工具时不输出无关解释”，减少过程文字，但不能依赖这句提示来省略分片处理。界面不展示工具参数 JSON、内部提示或模型思考内容。

查阅过程只作为当前请求的临时展示数据，完成的历史消息继续保存最终正文与来源，避免新增一套工具执行日志系统。

## 5. 前后端事件协议

沿用 `POST /api/me/ai/sessions/:id/messages`，请求体继续为提问内容；成功响应改为 `text/event-stream`。同批更新浏览器消费代码，其他会话与保存接口继续返回 JSON。

鉴权、参数、会话存在性和同会话并发限制，应在打开流之前完成；这一阶段的失败使用原有 HTTP 错误响应。流开始后发生的失败通过业务事件表达，不再尝试向同一响应追加普通 JSON 错误页。

| 事件 | 核心数据 | 客户端动作 |
| --- | --- | --- |
| `started` | 会话 ID、已落库的用户消息和助手消息 ID | 将临时消息原位关联到真实消息，保持稳定渲染标识 |
| `round-start` | 消息 ID、轮次 | 创建当前轮次的文本块 |
| `text-delta` | 消息 ID、轮次、增量文本 | 追加到指定文本块 |
| `round-end` | 轮次、`tool` 或 `answer` 类型 | 确定该轮属于查阅过程还是最终正文 |
| `phase` | 正在查找、正在阅读、正在整理及实际记录数 | 更新同一消息内的进度说明 |
| `completed` | 落库后的完整助手消息、最终轮次、来源 | 用最终结果收敛状态，开放保存文章 |
| `interrupted` | 消息 ID、原因、已生成的部分正文 | 保留文字并标明未完成，禁用文章保存 |

业务事件使用共享的可区分联合类型和 Zod schema。事件中的会话与消息标识由服务器生成；客户端按请求开始时捕获的会话处理，不按当前选中的会话处理。

`completed` 是本业务成功的唯一标志。上游某一轮的 `[DONE]` 不是整个 Agent 完成；浏览器读到 EOF 也不是成功。如果没有业务终态就断流，应明确显示本轮中断。

## 6. 前端展示与交互

### 打字观感

收到实际文本增量就追加到当前文本块，Vue 更新对应消息。首版接受每次出现一到几个字符的自然增量，不强制人为设置每个汉字的固定延迟，也不等整段回答生成后播放动画。

输出末尾显示简单 CSS 光标，完成或中断时移除。无需动画库。若真实使用中出现过密更新，再将小增量合并到约 30 毫秒的界面刷新批次；这只是渲染节流，不延迟网络读取，不逐字重新解析整段 Markdown。

项目禁止的 RAF 相关 API 不进入实现。需要刷新后定位时使用 Vue `nextTick`；读取与取消通过显式业务函数组织，不新增 watcher 驱动网络请求。

### Markdown 与消息状态

- 继续使用 `renderAiMarkdown`；流式正文同样走现有受约束的渲染路径，不将模型文本直接作为可信 HTML。
- 尚未闭合的代码块、强调和链接允许在后续增量到达时自然补全。首版不为此更换富文本编辑器或引入流式 Markdown 框架。
- 当前 `pending` 分支会隐藏正文，并把正数消息 ID 视为“本轮未完成”。接入流式时必须改为根据该会话是否持有活跃请求判断，不能继续按 ID 正负判断。
- 生成中显示已收到的正文；中断显示部分正文加中断原因；仅收到 `completed` 后可保存文章。

### 滚动与切换

输入框和站点框架常驻，更新范围仅为当前消息。用户位于底部时跟随输出；主动向上阅读后暂停跟随，显示“查看新回答”，点击后恢复跟随。不能每个分片都对整页执行平滑滚动。

流读取器与控制器由现有会话 Store 持有。切换会话、打开来源或离开 AI 路由时，当前请求继续归属于原会话；切回复用已收到文本，不重新发送提问。卸载展示组件不等于取消问答请求。

## 7. 停止、中断与保存

首版建议提供“停止生成”。同一会话开始下一轮前，应完成上一轮的服务端释放，避免用户停止后立刻发送却遇到旧请求仍占用会话。

具体采用一条站主专用停止接口：`POST /api/me/ai/sessions/:id/messages/:messageId/stop`。服务器按会话和消息定位正在执行的请求，取消上游模型调用，等待其落库及释放完成后返回。消息标识用于避免迟到的停止操作误取消下一轮请求。

- 用户点击停止：按钮即时显示“正在停止”；取消信号贯穿当前模型流及后续工具轮，停止后的内容保存为 `failed` 并注明用户停止，不执行下一轮工具。
- 停止接口在该消息已终结时返回该消息当前结果；不创建新任务，也不重复生成。这样可以处理点击停止与模型刚好完成的交界时刻。
- 浏览器关闭、刷新或连接断开：服务端监听响应连接提前关闭，取消上游；不能将 POST 请求体正常读完当作用户断线。
- 退出登录：先中止 Store 持有的请求，再清空缓存；旧事件不能重新写入已退出的状态。
- 正常完成：先保存完整最终正文和来源、释放本轮执行占用，再发出 `completed`。
- 模型截断、工具出错、协议解析错误：直接结束本轮，保留已收到部分并说明失败；不自动重试、重连、补问或切换模型。

无需新增消息状态枚举：沿用 `pending / completed / failed`。调整现有失败落库方法，使中断原因与当时已生成的正文一起保存；用户停止也不能变成可保存文章的完整回答。

不按每个 token 写 SQLite，正常完成或可处理的中断时一次落库。服务进程突然退出时，尚在内存中的部分文字可能丢失，历史仍显示该轮未完成；本次不引入断点续传或后台恢复任务。

网络在落库成功后、业务完成事件送达前中断时，页面明确保留“未收到完成确认”；用户重新打开历史时以服务器保存结果为准，不自动重新生成。

## 8. HTTP 与代理链路

服务端流响应设置：

- `Content-Type: text/event-stream; charset=utf-8`
- `Cache-Control: private, no-store, no-transform`
- `X-Accel-Buffering: no`

发送首个 `started` 事件时立即开始响应，不等第一轮模型调用结束。使用 Fastify 原生流响应和 Node 流背压，不手写无限积累的发送队列。

仓库 `deploy/journal/feeds.xmcloud.buzz.conf` 中，`/api/me/...` 命中私有接口的 location：现有读取超时为 120 秒，该段没有显式关闭响应缓冲。Nginx 官方说明 `X-Accel-Buffering: no` 可以按响应关闭缓冲，因此首先采用这一最小改动。[Nginx 官方 proxy_buffering 说明](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_buffering)

这是仓库配置事实，不表示线上 OpenResty 与边缘代理一定相同。进入实际接入与发布阶段后，需要按既有 Journal 运维路径核对生效配置是否忽略该响应头、是否压缩聚合 SSE、是否缓存私有接口。若确需更改代理，只限定 AI 接口范围并保留原有站主接口相关配置。

现有 `deploy-release` 的主机资源安装分支没有安装此站点 conf，因此不能把“修改仓库 conf 后普通 push”当作该配置已经线上生效。流式应用响应头可以随应用发布；额外主机配置变更应单独落实到现有运维路径。

首次内容等待和分片间的静默仍受现有超时约束。首版不主动新增心跳、重连或延长全站超时；如果实际链路出现超时，应定位发生在哪一层后再调整。

## 10. 交付顺序与业务完成标准

先完成服务端事件链路和工具分片，再接入浏览器读取与消息更新，最后收尾取消、来源、文章保存及代理行为。作为一批局部迭代完成，不自动继承此前提交和 push 的授权。

完成标准：

1. 普通回答在模型尚未结束时就出现可读正文，中文与 Emoji 跨分片后仍完整。
2. 搜索、读取和连续追问仍正常，工具参数不进入回答，多个工具分片不会混合执行。
3. 同一会话只有一个活跃回答；切换会话、查看来源再返回，不重复请求或串入别的会话。
4. 用户上滑阅读时不被强制拉到底部；发送区在桌面与移动端保持可操作。
5. 停止后保留已输出内容，服务端释放完成后可再次提问；未完成回答不能保存文章。
6. 模型正常结束且数据库保存成功后才展示完成；截断、断流和失败有明确的不同呈现。
7. 经站点实际访问路径时能够持续收到分片，而非只在请求结束后收到整段内容。

流式传输本身不会按分片数多收模型 token；本方案不额外生成一次答案。实际 token 仍由每轮输入和模型输出决定，停止动作也不能保证已经生成的内容不计费。本次不承诺固定首字耗时或动画帧率。
