## 后续可独立推进的批次

各批次需要用户另行确认，不因本次更名而自动获得提交、部署或外部环境修改权限。

### 1. 发布本批文件

用户授权后，提交本地元信息、README、AGENTS 和本文，再推送到现有 `main`。沿用现有 GitHub Actions 路径，不为了项目更名手动强制部署服务。发布后更新本文的提交和发布状态。

### 2. 子包名称统一

可将两个子包的命名空间统一为 `@mingworks`，应用目录不变。包名与 Lu Dockerfile、start.gg 工作流中的包选择条件必须同步调整；依赖版本不随之升级。此批涉及交付链路，不能与纯 README 改名等同处理。

### 3. 本机目录迁移

目标目录可采用 `/Users/xiaomingli/Code/MingWorks`。联动项是 `scripts/notinews-video-worker` 中的绝对路径、对应 SSH 强制入口及编辑器工作区。先确定当前实际使用这些路径的进程和外部入口，再迁移目录；不添加长期兼容软链接。

本次盘点只在仓库中找到 Mac SSH 强制入口示例，当前用户默认位置没有 `authorized_keys`，Bot 的 `.env` 中也未找到 Mac 下载连接项，不能据此把这条链路视为已启用。后续以当时的实际配置为准，不为更名补建下载环境。

### 4. Bot 目录与服务名称迁移

此批需要维护窗口，不适合零散替换。先保存当时的数据和配置，再协调 Bot、下载任务、备份任务及 Lu 对同一数据目录的使用。

必须联动的项目包括：

- 服务器项目目录及 GitHub Secret `SERVER_PROJECT_DIR`。
- Bot 与失败通知服务的工作目录、环境文件路径及服务关联。
- 下载任务的工作目录和锁路径、已安装的备份脚本、备份定时器。
- Lu 的数据目录挂载，以及 start.gg 服务对 Bot 服务的依赖。
- 备份健康监控中的服务名称、恢复脚本的目标目录和旧归档内的服务定义。

不能只改 Secret 或创建一个空目录：现有 `.env` 和数据必须随迁移保留，Bot 与 Lu 必须继续使用同一份数据库。旧备份可能恢复到历史代码和旧服务路径；其恢复方式需要单独明确，不能因归档仍存在就宣称恢复路径也已适配。

### 5. 容器与镜像名称统一

Journal 与 Lu 可以分别安排迁移。镜像标签、Compose 容器名、工作流和服务器上已安装的发布脚本必须同批更新；Journal 备份任务引用容器名，Lu 代理配置引用容器网络名称，也必须同步。

视频下载辅助容器另有自己的安装脚本和端口占用关系，需单独纳入明确范围。所有容器更名均保留原有数据挂载，不另建一套空数据。

### 6. 其他运行标识与显示文案

Bot 欢迎信息、异常通知、发布通知及 HTTP User-Agent 可以在后续业务发布时统一。SSH 密钥文件名、下载工作目录和锁名、rclone remote 名称需要与实际使用端同步，不重新申请密钥或修改授权本身。

Journal 的浏览器主题与导航样式存储键可以长期保留；直接改键会让已有偏好读不到，若将来需要更名，应先明确偏好保留要求。

## 不作为后续必做项的数据更名

`data/notinews.sqlite`、云端 `NotiNewsBackups` / `NotiNewsDownloads` 目录、历史备份内部格式不必跟随项目品牌更名。尤其数据库路径变化可能创建新的空数据库，备份目录和格式变化会影响旧归档的查找及恢复。

默认继续保留这些名称。若将来明确要求清理到完全没有旧标识，应作为单独的数据迁移任务重新确定范围；不能全局替换，也不重写 Git 历史。
