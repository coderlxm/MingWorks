# Journal 后端 Go 快速迁移方案

日期：2026-10-05

适用条件：个人项目，最多 5 个用户；接受短暂停机、功能缺陷及切换后在线修复。

本方案与 [原方案](./journal-go-backend-refactor-2026-10-05.md) 并存，原文件保持不动。原方案的 22—35 个工作日估算撤回，本版按约半天的 AI 集中执行安排。

## 1. 目标与取舍

**用约 4 小时集中完成 Journal 全量 Go 后端的第一版替换，接入现有前端，在独立环境实际使用后切换。** 半天是执行目标，具体耗时和剩余问题以实施结果为准。

所有现有后端模块都在本轮迁移范围内。允许部分功能带着缺陷上线，随后直接在 Go 中修复；不得用空结果、虚假成功响应掩盖尚未完成的接口。

这次迁移主要解决后续后端开发统一使用 Go 的需求。AI、Google Drive 等外部请求和媒体处理的耗时，仍受上游服务与原生工具影响。

与原方案的主要区别：

| 项目 | 本版处理方式 |
| --- | --- |
| 排期 | 半天集中实施，按实际问题修正安排 |
| 功能范围 | 同一轮迁移全部模块，允许缺陷，避免长期维护两套后端 |
| 数据 | 沿用 SQLite、现有表结构和文件目录 |
| 前端 | 继续使用现有前端，以当前请求和响应作为接口依据 |
| 工程配套 | 直接写 Go 业务代码，不把 OpenAPI、代码生成、新迁移框架列为前置工作 |
| 验收环境 | 同一台服务器上的一个独立实例和一份数据副本 |
| 切换 | 短暂停机，一次切换，随后在线修复 |

## 2. 分支和代码范围

使用已经创建的 **`refactor/journal-go`** 分支。新后端放在 **`apps/journal-api`**，优先按业务模块组织文件，避免提前拆出大量接口层、抽象层和独立服务。

迁移范围包括：

- 登录、管理员操作、文章与生活记录、标签、主题、公开阅读和搜索。
- 自动化文章接口、Telegram 写入接口、投稿链接及投稿管理。
- 文件上传、tus 续传、图片预览、视频处理、媒体访问。
- AI 对话、知识搜索、引用和生成文章。
- Drive 相册、天气、游戏、留言、点赞、简历、个人资料及订阅输出。

以 `src/journal-server` 当前源码及其实际引用的共享逻辑为迁移依据。前端、独立 Telegram bot 和现有文章 CLI 继续通过 HTTP 使用 Journal；只调整迁移直接需要的接口接线。

原 Node 后端源码暂时留在仓库中供对照。切换后的 Journal 服务及其后台处理全部由 Go 执行，镜像不依赖 Node，也不把未完成模块转发回旧服务。

本轮必要的部署改动集中在新后端目录、Journal Dockerfile、容器健康探测，以及现有 workflow 的后端路径匹配规则。

## 3. 技术选型：直接采用成熟组件

以下沿用本轮已经查阅的官方项目资料，实施时固定实际采用的依赖版本。

| 能力 | 选择 | 使用方式 |
| --- | --- | --- |
| Go 与 HTTP | Go 1.27.1、`net/http`、chi v5、`log/slog` | 普通单体服务，保留现有 URL、状态码和错误字段 |
| SQLite | `database/sql` + `mattn/go-sqlite3` | 直接迁移现有 SQL，保留事务和约束 |
| tus 上传 | tusd v2 | 嵌入 HTTP 服务，接上现有上传授权和完成处理 |
| 图片 | govips / libvips | 承接 Sharp 的缩放、格式转换和预览生成 |
| 视频、HEIF、PDF | 继续使用 FFmpeg、libheif、Poppler | 沿用现有处理参数和工具能力 |
| 富文本与 Markdown | Goldmark、bluemonday、html-to-markdown | 通用解析使用库；补齐项目实际使用的 Tiptap JSON 映射 |
| AI、Drive、Telegram | OpenAI Go SDK、Google Drive Go SDK、go-telegram/bot | 保留现有提供方、模型、工具调用和外部接口 |
| 订阅 | gorilla/feeds | 保留现有订阅地址和内容字段 |

SQLite 驱动和图片库都涉及原生依赖，镜像一次性包含所需的运行库，以及现有媒体工具。使用上述 SDK 时关闭自动重试，错误直接暴露。

本轮继续沿用 SQL 搜索、进程内缓存和上传会话，不增加 Redis、队列、向量数据库。数据库访问直接使用 SQL；现有结构没有变更需求时，不引入 sqlc 或 goose 作为迁移前提。

官方资料：[Go 版本](https://go.dev/doc/devel/release)、[chi](https://github.com/go-chi/chi)、[SQLite 驱动](https://github.com/mattn/go-sqlite3)、[tusd 嵌入方式](https://tus.github.io/tusd/advanced-topics/usage-package/)、[govips](https://github.com/davidbyttow/govips)、[Goldmark](https://github.com/yuin/goldmark)、[bluemonday](https://github.com/microcosm-cc/bluemonday)、[HTML 转 Markdown](https://github.com/JohannesKaufmann/html-to-markdown)、[OpenAI Go SDK](https://github.com/openai/openai-go)、[Drive SDK](https://pkg.go.dev/google.golang.org/api/drive/v3)、[Telegram SDK](https://github.com/go-telegram/bot)、[订阅库](https://github.com/gorilla/feeds)。

## 4. 真正需要花精力的地方

### 数据与现有接口

直接沿用 `journal.sqlite` 和资产目录，保留 ID、表字段、索引、文件相对路径及密码哈希。当前源码的迁移版本为 24；切换时以实际数据库结构为准。已有库不因更换语言而重新建表或重写内容。

前端请求、CLI 和 bot 调用就是接口依据，迁移时对照实现。重点保留 JSON 字段、空值表达、分页、媒体地址、错误字段以及 SSE 事件名。旧登录态可以失效，重新登录即可；文章密码与已有内容继续可用。

### Tiptap 富文本

这是本次最明显的非直接替换部分。现有正文存储为 Tiptap JSON，Go 中需要承接实际使用的节点、属性与正文提取，并连接 Markdown 导入导出和订阅渲染。

保留原始 JSON，不转换或清洗历史正文。优先覆盖当前编辑器实际支持的段落、标题、列表、代码、图片和表格；复杂格式的展示或导出差异可以留到切换后修。不能为了让转换通过而静默删除不支持的内容。

官方 [Tiptap HTML 工具](https://tiptap.dev/docs/editor/api/utilities/html) 仍依赖 JavaScript 扩展体系，这一部分需要项目内映射，不能把某个 Go 库当作完整平替。

### 上传、媒体与 AI

上传继续使用 tus 协议和现有资产归属规则，图片与视频保留现有处理方式。暂停服务导致正在进行的上传中断可以接受，用户重新上传即可。

AI 继续连接现有 DeepSeek 服务，迁移流式输出、停止操作、知识工具调用和生成文章，不调整模型或重做检索。Drive、天气等模块按现有行为迁移。

这几部分集中对接真实主路径。边角交互、少见格式和展示差异允许带着问题上线，明确记录后直接修复。

## 5. 半天执行安排

时间段是 AI 连续实施的工作预算，不是已经证实的完成时间，也不按模块逐个叠加工期。

| 时间预算 | 直接完成的工作 |
| --- | --- |
| 0—30 分钟 | 整理当前路由与外部依赖；建立 Go 服务入口，接 SQLite、配置、登录和静态资源 |
| 30—150 分钟 | 集中迁移全部业务模块，包含富文本、上传、媒体、AI 和外部服务 |
| 150—210 分钟 | 完成镜像与现有发布链路接线，放到独立环境，通过实际使用处理主路径问题 |
| 210—240 分钟 | 整理已知问题；进入已授权的发布阶段后，一次切换并处理真实使用中暴露的问题 |

到时间点就报告实际状态：哪些能力已接通、哪些仍有问题、具体卡在哪里。遇到某个库或协议对接耗时超出预算，围绕该问题继续处理，不把整个迁移重新扩成多周工程。

## 6. 最小验收环境

沿用 `rndc02`，增加一个独立 Go 实例即可：

| 项目 | 安排 |
| --- | --- |
| 容器 | `notinews-journal-go-preview` |
| 目录 | `/opt/journal-go-preview` |
| 数据 | `/opt/journal-go-preview/data`，使用生产数据与资产的一份副本 |
| 前端 | 复用当前已发布的前端产物，由 Go 服务同源提供 |
| 监听 | 服务器回环地址 `127.0.0.1:3101` |
| 访问 | 通过现有 SSH 连接做本地端口转发，在本机 `http://localhost:3101` 使用 |
| 配置 | 独立 `.env`，设置预览地址、数据目录和验收用的外部发送目标 |

数据库副本通过 SQLite 一致性快照取得，资产复制到独立目录；预览容器仅挂载这份副本。正式 bot、CLI 继续连接生产入口，预览操作不能写入生产库。

前端使用同源 API，避免沿用当前 Vite 开发代理中指向生产的地址。验收入口直接提供前端产物，省去新增开发服务、域名和独立自动发布系统。

验收方式就是按日常习惯实际用一次：登录、打开旧文章、发布带图内容、做一次 AI 对话。其余功能有问题直接记录，不以全模块零缺陷作为切换条件。

## 7. 一次切换，随后修问题

开始正式发布后，沿用项目现有的 **提交 → push 到 main → GitHub Actions → 观察真实发布结果** 路径。现有 workflow 增加 `apps/journal-api/**` 的后端变更识别，继续使用原镜像名称、容器、端口和发布脚本。

切换前短暂停止旧后端写入，完整复制当时的数据库和资产，保留一份切换前数据。Go 接管原来的 `/opt/journal/data`，前端和对外地址继续沿用现有值。验收库只用于体验，不覆盖生产数据。

可以接受上线后修复的情况：重新登录、正在进行的上传中断、部分模块报错、特殊富文本格式差异、次要页面行为不一致。

需要先处理的实际阻塞：Go 服务无法启动、无法打开现有数据库，或者迁移逻辑会覆盖、删除已有内容。保留旧镜像与切换前数据，便于必要时手动处理；不增加自动回切或双服务转发。

第一轮交付就是 Go 后端源码、对应镜像与发布接线、独立验收入口，以及简短的已知问题清单。切换后的功能修复继续在 Go 后端完成。
