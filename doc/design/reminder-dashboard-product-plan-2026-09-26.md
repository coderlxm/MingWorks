# 提醒看板产品方案：拾时

> 状态：已确认，按 P0 实施 · 2026-09-26
>
> 用户已确认视觉方向：**温暖、轻盈的生活日程风**。
>
> 本文定义产品范围、页面、交互和后续实现边界。用户已确认按本方案与视觉稿进入实现和部署；以下“当前能力”记录方案形成时的源码情况。

**应用目录：** `apps/reminder-dashboard`。中文名“拾时”，英文标识为 Reminders。

**视觉附件：** [打开静态视觉稿](./reminder-dashboard-preview.html)。其中日期、提醒和状态均为示例，仅用于讨论风格、布局与新建入口。

## 1. 产品目标

为现有 Telegram Bot 增加一个个人提醒管理入口：用 Telegram 随手记录、接收到点消息，用网页查看全局、整理规则和调整安排。两个入口操作同一份提醒。

打开看板，应很快回答四个问题：

1. **现在有什么需要我处理？** 已发来但尚未确认的提醒集中呈现。
2. **接下来会提醒什么？** 今天、明天和未来七天的时间安排清楚可见。
3. **哪些事情在重复提醒？** 能查看、调整、暂停、恢复和结束循环规则。
4. **怎样让提醒适应今天？** 可以延期、取消、确认完成，生活专项可以停止今天的提醒。

产品按单用户工具设计。私人提醒全站登录后可见；通知仍由现有 Telegram Bot 发送。页面关闭后，Bot 继续调度。

### 成品应有的感觉

像一本清楚、安静、随手可改的电子日程本：时间轴是视觉中心，下一件事容易找到，操作有回应，完成之后页面自然变轻。首页采用简短数量摘要，不用大面积统计卡片占据首屏。

### 范围划分

- **主要管理对象：** 一次性提醒、循环规则及其每次触发、维生素／打卡／下车三类生活专项。
- **生活提醒的补充区域：** 睡觉、起床、咖啡、拍照、Lu 记录提示。按提示类规则管理，不要求用户逐条勾选完成。
- **保留各自业务入口：** 赛事监控、AV 订阅、Steam 价格关注。它们不会混入首页待处理数量。
- 新闻、英语、GitHub、V2EX、服务器与备份巡检属于其他定时推送或运行任务，本轮提醒看板不增加对应管理界面。

当前固定专项没有完整的网页配置能力。方案中的开关、改时间、停止当天，涉及后续补充少量持久配置和调度操作，不能仅靠增加表单完成。

## 3. 信息架构

| 页面 | 用户主要目的 | 主要内容 |
| --- | --- | --- |
| **今天** | 处理眼前的事，安排接下来 | 待确认、今日时间轴、未来七天、快捷添加 |
| **全部提醒** | 找到和整理提醒 | 一次性提醒列表，关键词、日期和状态筛选；循环规则及生活专项入口 |
| **循环规则** | 管理重复安排 | 运行中／已暂停／已结束，规则摘要，下一次时间，规则详情及触发记录 |
| **生活提醒** | 管理日常专项 | 维生素、打卡、下车，以及固定生活提示区 |
| **历史** | 查看过去发生了什么 | 已确认、跳过、取消、自动结束、错过、发送异常；按日期与类型筛选 |

顶部常驻：品牌、当前页面、新建按钮、最近数据更新时间、账户入口。显示时区“北京时间”；状态说明使用可理解的中文，不显示内部表名、调度表达式或数据库 ID。

账户菜单收纳退出登录、时区和通知目的地说明；主题切换随后续暗色主题一起提供。首期通知固定发送到已配置的个人 Telegram 会话，不提供收件人管理。

## 4. 核心页面与操作

### 4.1 今天：待确认在前，时间安排在后

**待确认区**展示已发送、尚未处理的提醒。跨日未处理项保留原日期，如“昨天 20:00 发出”，不悄悄混成今天的新提醒。

**时间轴**按当天真实计划排序，显示绝对时间、内容、类型和一句规则摘要。距离很近的提醒可补充“约 10 分钟后”，绝对时间始终保留。无需每秒跳动。

**未来七天**采用分日列表，复用同一页面框架。循环规则在未来视图中展开为预计发生的事项，点击可进入所属规则；尚未触发的预计事项不生成虚假的历史记录。

每行只放最常用的 1–2 个动作，其余进入详情或更多菜单。状态不同，动作随之变化：

| 对象 | 直接操作 | 详情中的操作 |
| --- | --- | --- |
| 尚未触发的一次性提醒 | 编辑时间 | 编辑内容、提前完成、取消 |
| 已发送的一次性提醒 | 完成、稍后 | 指定新时间、取消 |
| 已触发的循环提醒 | 完成本次、跳过本次 | 查看规则、暂停规则 |
| 预计将来的循环事项 | 查看规则 | 修改规则；首期不提供单独拖动某一天 |
| 维生素当天提醒 | 已吃、30 分钟后 | 今天不再提醒、查看规则 |
| 打卡当天提醒 | 我已打卡 | 今天不再提醒、查看规则 |
| 下车当天提醒 | 已下车 | 今天不再提醒、查看规则 |

完成动作返回成功后，该行明确变成“已完成”，随后移入“今天已处理”；保留用户当前视口，避免列表突然跳到顶部。

随机安排在具体时刻尚未确定前显示“20:45–21:00 之间”。只有 Bot 已保存实际安排时间后，才能显示精确下一次时间。

### 4.2 新建与编辑：一个入口，两种输入方式

桌面使用右侧抽屉，手机使用全屏表单。新建、编辑复用同一套字段和规则预览。

**表单输入为完整主路径：**

- 内容：提醒自己做什么。
- 类型：一次性／循环。
- 一次性：日期、时间；提供 5／15／30／60 分钟后等快捷选择。
- 循环：每天、每周指定星期、每月指定日期、中国工作日；选择具体时刻。
- 时区：首期统一北京时间；既有其他时区规则必须明确显示原时区，不能编辑时偷偷转换。
- 预览：保存前显示完整语句及下一次时间，例如“每个中国工作日 09:20 提醒，下一次为……”。

**自然语言为 P1 的可选输入方式：**

输入“明天晚上八点提醒我收衣服”，点击“识别”，解析结果填入同一个表单。用户确认时间与内容后再保存。解析失败原地显示原因并保留输入，不自动创建另一种提醒。

**快捷模板：**沿用现有六种预设；点击后填好内容和时长，仍可调整并确认。第一版无需增加独立模板管理系统。

规则细节需要在输入时讲清：

- “中国工作日”和“周一至周五”分开选择；调休以中国工作日日历为准。
- 每月 29／30／31 日，按实际存在的日期触发；明确说明无该日期的月份不会触发。
- 新建及改期时间必须在未来；打开抽屉后时间已经过去，也不能保存为过期时间。
- 编辑循环规则影响尚未触发的后续安排；已经发出的当次提醒保留原来的内容和时间。
- 关闭有改动的表单时确认是否放弃；取消放弃后回到原草稿，重新打开不出现上一条记录的数据。

### 4.3 全部提醒：便于查找、调整和取消

默认显示有效的一次性提醒，提供关键词、时间范围和状态筛选；循环与生活专项有明确入口，不把规则和每次发生重复计数。

列表显示内容、计划时间、发送／处理状态及常用动作。点内容打开详情；行内按钮不同时触发详情。

取消提醒使用明确文案“取消这条提醒”，取消后保留历史。已完成和已取消内容可复制为新提醒。首期不增加永久清空历史、批量删除或全局一键停用。

筛选、选中项及滚动位置应在详情关闭、切换页面再返回时保留。没有匹配结果时显示当前筛选条件及清除入口；整个列表为空时提供新建入口。

### 4.4 循环规则：管理规则，也能看每一次

每条规则显示内容、频率、时间、下一次、运行状态；展开后看到下一周预览与已发生记录。

- **暂停：**停止后续触发；已发出的待确认项继续保留。
- **恢复：**从当前时间计算下一次有效触发，明确展示恢复后的时间，不自动补发暂停期间的次数。
- **结束规则：**终止后续触发，保留过去记录；确认文案说明影响整条规则。
- **完成／跳过本次：**只作用于明确的一次触发，不修改下一次计划。

第一版支持对已经触发的实例“跳过本次”。提前跳过未来某一天、只改某一次时间、给某次循环单独延期，都需要额外的日期例外规则，列为后续增强，界面不提前展示无效按钮。

### 4.5 生活提醒：当天动作与长期规则分开

每个专项使用一张紧凑卡片，分为“今天”和“提醒规则”。今天显示状态及动作，规则显示启用情况和时间说明。

| 专项 | 当天管理 | 规则管理建议 |
| --- | --- | --- |
| 维生素 | 已吃、30 分钟后、今天不再提醒；显示下次时间 | 长期启停；工作日随机窗口、非工作日固定时刻；首期保留 30 分钟间隔 |
| 打卡 | 我已打卡、今天不再提醒；显示待确认或已结束 | 长期启停；保留当前随新闻发出、09:59 补提醒、10:00 截止的关联说明 |
| 下车 | 已下车、今天不再提醒；显示已提醒次数与下次时间 | 长期启停；工作日首次时刻；首期保留间隔 2 分钟、最多 3 次 |

“今天不再提醒”单独记录为主动停止，次日仍按规则运行；长期关闭立即停止当前专项剩余提醒，未来也不触发；重新启用从下一个未来有效时刻开始，不立即补发过去的安排。

首期不提供打卡时间的独立编辑：它当前与新闻流程关联。若后续允许自由改打卡时间，需要先把“打卡提醒的触发”与“新闻内容的发送”拆开，避免只改页面时间却不改变真实触发。

固定生活提示放在页面下半部，展示睡觉、起床、咖啡、拍照和 Lu 提示的安排，不进入待确认清单。首期仅显示当前规则与预计提示时间；接入对应的发送记录后才能显示“本次已发送”。下一轮再增加对应启停及时间编辑。

### 4.6 历史：说明结果，不编造统计

按日期展示计划时间、内容、类别、发送结果和用户动作。提供最近 7 天／30 天及自选日期，默认从新到旧按需加载。

- 已发送不等于已完成；“已完成”需要用户确认。
- 跳过、取消、主动停止、自动到期分别表达。
- 发送异常展示这次异常和计划时间，用户可以明确选择改期；不自动重试或补发。
- 当前旧数据无法区分的记录，显示“历史提醒已处理，结束原因未记录”等明确说明。
- 旧维生素记录没有可靠完成时间；旧打卡和下车记录可能由系统自动关闭，不能据此计算完成率、出勤率或连续打卡天数。
- 旧一次性提醒的 cancelled 也可能来自重启时自动取消；旧循环实例可能在发送前已创建。缺少对应证据时，分别保留取消原因未知、发送结果未知。

## 5. 状态与数据语义

### 5.1 页面至少区分这些状态

| 状态 | 必须具备的依据 | 页面表现 |
| --- | --- | --- |
| 待触发 | 有未来有效计划 | 时间及“待提醒” |
| 已发送待确认 | 有这次触发的发送成功依据，尚无处理动作 | 进入待确认区，显示发送时间 |
| 已延期 | 用户明确设置了新的未来时间 | 展示新时间和“已延期”，不沿用上次发送状态 |
| 已完成 | 用户明确确认该条／该次／该日 | 完成状态及可用的确认时间 |
| 已跳过／主动停止 | 用户明确跳过当次或停止当天 | 保留具体动作，后续规则继续有效 |
| 已取消／规则已结束 | 用户终止了这条提醒或整条规则 | 进入对应历史或已结束分组 |
| 自动结束 | 到达截止或次数上限 | 显示结束原因，不标记为完成 |
| 已错过 | 计划已过，未发送且没有未来调度 | 说明已错过，允许用户改期 |
| 发送失败 | 有真实发送异常 | 原地显示错误，不呈现成功状态 |
| 历史结果不明 | 旧字段不足以区分结果 | 显示已有信息及缺失说明 |

### 5.2 看板落地前需要处理的主路径

1. **一次性提醒不能只用 pending 判断“待提醒”。** 当前发送后仍是 pending；稍后操作也可能保留旧消息 ID。需要记录或关联本次计划与本次发送结果，才能正确显示下一次状态。
2. **重启后保留正确的待确认语义。** 当前恢复逻辑会取消过期 pending，包括已经发送但未确认的情况。拟调整为：已发送项继续待确认；确实未发送的过期项显示已错过，由用户决定改期。
3. **专项操作绑定日期。** 网页请求和 Telegram 按钮都指向明确日期；旧日期动作不得完成今天的维生素，也不得启动今天的循环。过期操作显示已失效。当天循环到北京时间午夜结束，次日由自己的规则安排；稍后时间跨日时，明确提示这次操作超出当天范围。
4. **关闭原因分开保存。** 从新版本开始明确记录用户确认、主动停止和自动结束；旧记录保持未知原因，不倒推补造。
5. **规则修改保留过去。** 已发生实例需要保留当时内容、计划时间和结果，修改规则不能改写历史文案。
6. **规则配置真实影响调度。** 修改、暂停、恢复以及专项开关必须更新 Bot 内存中的任务和持久数据；刷新页面后仍保持一致。
7. **随机窗口真实呈现。** 随机时刻确定后保存该安排，服务恢复复用已确定的时间；尚未确定时只展示时间窗口。
8. **中国工作日数据缺失要明确报错。** 不能把缺失日历的安排显示为已确认的中国工作日结果；当前通用循环和固定任务的日历读取方式存在差异，接入看板时需统一涉及本范围的计算口径。

这些是随 P0 看板一并落地的必要补齐。记录只服务于提醒展示和处理，不扩展成通用审计平台。

## 6. 页面加载、刷新与 Telegram 联动

### 首次进入

先确定登录状态。登录后常驻框架稳定展示，日期区与列表在原位置加载。若采用开场动画，动画覆盖到默认页面首屏必要数据就绪；历史详情和其他页面数据不阻挡首屏。会话过期时遮住私有内容并显示登录入口；重新登录后回到原视图，不自动提交未保存的表单。

首屏请求失败就结束动画，在对应区域展示明确原因和手动重新加载入口，不能无限遮罩或显示成“今天没有提醒”。

### 正常使用

- 页面可见时建议每 **15 秒**拉取当前视图数据；这是网页状态同步周期，不是 Bot 提醒触发精度。Bot 仍按既有服务端调度触发。
- 同一视图至多一个读取请求在途；切到后台停止周期读取，正常状态下回到前台立即读取一次。
- 读取失败后显示错误和最后成功更新时间，停止该轮周期读取；由用户点击重新加载后恢复，不做自动重试，也不因切换前后台自动重试失败的读取。
- 已加载的内容继续显示并标记“数据尚未更新”；不能在失败时伪装成空列表或显示“实时同步中”。
- 编辑抽屉中的草稿不会被刷新覆盖。只读列表发生变化时局部更新，滚动位置和焦点保持。
- 移动端浏览器恢复页面时同步当前视图，旧的倒计时与“今天”日期一起更新。

### 修改与反馈

操作立即进入提交状态，成功由服务端返回的真实结果驱动；失败保留表单和原状态，显示具体错误。提示紧邻操作对象，消息消失后仍能从状态看出结果。

同一提醒在 Telegram 已被处理，网页再次操作时显示最新结果，不把它覆盖回旧状态。保存时服务端核对对象当前状态和对应触发实例；过期页面提示重新载入该项。

Web 创建和编辑成功后，默认在网页反馈，不额外发送一条“配置成功”消息。到点提醒继续发往 Telegram。完成、取消、暂停等动作复用或更新已有卡片及按钮；不为每次网页操作制造新的消息。

数据库已更新但 Telegram 卡片更新失败时，要明确显示“状态已更新，Telegram 卡片更新失败”，不能把整个操作描述为全部成功，也不能自动换一条消息发送。

## 7. 视觉方案：温暖、清晰、克制

### 7.1 视觉语言

| 项目 | 建议 |
| --- | --- |
| 页面底色 | 暖米白 `#F5F3ED`，给长时间阅读留出柔和背景 |
| 内容底色 | 纸白 `#FFFEFA`，用细边框区分层次 |
| 主文字 | 深墨绿 `#24382F`；说明文字保持足够清晰，避免大面积浅灰小字 |
| 主操作 | 深鼠尾草绿 `#476650`；浅绿仅用作选中背景和轻提示 |
| 临近／待确认 | 陶土色 `#A45C36` 搭配浅杏背景，少量强调 |
| 异常／取消确认 | 低饱和深红，配明确图标及文字 |
| 字体 | 使用本地系统中文字体；日期、时间采用清晰稳定的数字排版 |
| 圆角 | 主要面板约 16px，输入与按钮约 10px；标签轻巧，避免全部胶囊化 |
| 层级 | 大日期、小摘要、清楚的时间列；轻分割线优先于重阴影 |
| 品牌 | 简洁时间／叶片线条标记，和 favicon 同步设计 |

列表内容字号以 15–16px 为主，说明以 13–14px 为主。详情中给正文足够空间，不强行把完整内容截成单行。图标以统一线条风格呈现，少量生活图形用于快捷入口。

暗色主题作为后续视觉补充，采用暖深灰与柔和绿；首期优先把用户确认的浅色方向完整落地。

### 7.2 微交互

- 状态切换、抽屉进入采用约 160–220ms 的短过渡，不使用持续闪烁或循环装饰动画。
- 完成反馈是文字、图标和分组变化；不设置烟花、音效或积分奖励。
- 焦点、悬停和按下状态清楚；颜色之外仍有状态文字。
- 系统要求减少动态效果时，取消非必要过渡，参照 [MDN 的 prefers-reduced-motion 说明](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@media/prefers-reduced-motion)。

### 7.3 手机与键盘体验

窄屏采用单列日程，保留紧凑顶栏；底部提供今天、提醒、生活、历史四个入口，循环规则从“提醒”进入。新建按钮始终易于触达，输入时不被软键盘遮住。桌面右侧辅助栏在窄屏移到正文后，不挤压时间轴。

主要触控区按约 44px 设计，给相邻按钮留间距；这是本产品的舒适操作目标。W3C 对目标尺寸与间距的原则见 [Target Size (Minimum)](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)。

键盘可完成新建、编辑与筛选；抽屉打开后焦点进入表单，关闭后回到原入口。固定顶栏和底栏不能遮挡键盘焦点，参照 [Focus Not Obscured](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html)。

## 8. 落地方式与范围控制

### 建议承载方式

```text
apps/reminder-dashboard
  └─ 独立提醒页面与私有登录入口
       └─ 同域请求进入页面服务
            └─ Bot 进程内的提醒业务接口
                 ├─ 现有提醒数据库
                 ├─ 当前调度任务
                 └─ Telegram 原消息与按钮
```

参考 FTG 已有的页面服务与 Bot 内部 API 分工，采用独立提醒接口；网页写操作调用 Bot 业务动作。直接改 SQLite 无法同步清理定时器和 Telegram 按钮，因此不采用 Lu 的纯只读数据接入方式承载修改。

前端沿用仓库已使用的 Vue、TypeScript、Vite 体系。简单日程列表使用现有组件能力；第一版不需要引入大型日历、新的消息队列或第二套提醒调度服务。具体组件 API 和依赖版本在实施时按本地实际安装情况确定。

发布接入项目现有 main → GitHub Actions 路径，服务与 Bot 放在 `bwgdc01`；为新增应用补充 workspace、部署范围和服务配置。入口为 `remind.xmcloud.buzz`，页面服务使用端口 3420，Bot 内部接口使用端口 3421。

### 实施优先级

| 优先级 | 交付内容 | 完成后用户能得到什么 |
| --- | --- | --- |

## 9. 产品完成条件

这些场景用于说明产品应达到的效果，不替代后续对具体实现范围的确认。

1. 创建“一小时后收衣服”，今天页面立刻出现正确的未来时间；从 Telegram 创建也能同步显示。
2. 到点消息发送后，页面进入待确认；点击稍后后显示新时间，再次发出对应新的触发。
3. 网页完成或取消后，Bot 不再按原计划继续提醒；旧 Telegram 按钮无法把它重新变成待处理。
4. 打开编辑、取消关闭、继续编辑、放弃后重新打开，各阶段内容和焦点符合预期。
5. 暂停循环后下一次停止；恢复时明确显示下一个未来触发；完成一次不结束整条规则。
6. 页面停留到第二天，今天视图随之更新；昨日卡片仍只作用于昨日。
7. 打卡到点关闭和下车达到次数上限，显示自动结束；用户确认显示已确认。
8. 随机提醒尚未确定具体时间时展示窗口；确定后显示真实计划。
9. 刷新、切页、打开详情和关闭详情不会造成整页闪现、筛选丢失或回到列表顶部。
10. 首次加载失败有清楚错误；后续读取失败标明数据时间，不清空已有日程、不继续宣称同步正常。
11. 旧数据仅展示能证明的信息；页面中的数量不把规则、发生实例、内容推送重复计入。
12. 手机可以顺利完成新建、延期、确认和规则管理，常驻导航不遮挡最后一项内容。

## 10. Review 建议

建议按以下顺序讨论：

1. **整体布局：**“待确认＋今日时间轴＋快捷添加”是否符合日常使用习惯。
2. **首期范围：**P0 覆盖通用提醒及三个生活专项；其他固定生活提示在首期只展示，配置放到 P1。
3. **管理语义：**完成本次、暂停规则、结束规则、今天不再提醒是否足够清楚。
4. **视觉与命名：**浅色方向已确认，进一步 review 视觉稿的密度、留白和暂定名“拾时”。

用户已确认进入 P0 实现阶段，并授权沿现有流程提交、push 和部署。访问入口定为 `https://remind.xmcloud.buzz`，交付操作项见[用户验收清单](../acceptance/reminder-dashboard-2026-09-26.md)。
