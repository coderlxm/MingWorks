# AI 入口：个人知识助手 MVP

日期：2026-09-12。阶段：方案设计，尚未进入功能实现。

用户已确定：首版围绕站内记录、文章进行查找、总结和整理。以下功能边界与交互为本次建议，不代表现有功能。

## 1. 首版定位

一个仅供站主使用、能查阅 Journal 内容的个人知识助手。用一句自然语言找回以前记下的内容，结合原文回答问题，再把有价值的讨论整理成可继续编辑的私有文章。

首版闭环：**提问 → 助手查找并阅读记录 → 给出带来源的回答 → 连续追问 → 按需保存整理结果。**

最值得先解决的是“东西存过，但想不起在哪里”和“记录散落，重新组织费时间”。已有搜索仍适合明确关键词查找；AI 的新增价值在于理解问题、选择要读的材料，以及跨记录组织答案。因此首版不需要另建知识库或导入流程。

### 三个核心场景

| 用户输入示例 | 助手行为 | 用户得到什么 |
| --- | --- | --- |
| “找一下我之前记过的 Cloudflare 部署内容” | 提取关键词，查找标题、正文和标签，读取相关内容 | 简短说明及可打开的来源 |
| “根据这些记录，总结当时遇到的问题和解决办法” | 沿用上一轮来源，必要时读取更多正文 | 按问题组织的总结，区分原文事实和推断 |
| “把刚才这些整理成一篇笔记，保留参考来源” | 在对话里生成完整整理稿 | 预览后点击“保存为私有文章”，进入现有编辑器 |

示例只描述预期能力，不表示站内实际已有这些内容。

## 2. 首版范围

### 必须包含

- 自然语言检索：支持关键词、标签、时间范围；“上周”等时间按 Asia/Shanghai 解释，并在回答中显示实际日期范围。
- 基于原文的回答：找回记录、概括主题、对比几条记录、整理文字。
- 连续对话：理解“这几篇”“第二条”“刚才的结论”等当前会话指代。
- 来源引用：回答中的关键结论关联到具体记录，显示标题、日期与正文片段。
- 简单会话历史：新建、切换和删除会话；刷新后可继续阅读已完成的问答。
- 整理结果保存：用户主动点击，将选定整理稿保存为私有文章，保留来源并标记 AI 生成。

### 本版不包含

联网搜索、外部网页抓取、附件上传与解析、图片识别、音视频转写、自动长期记忆、跨会话偏好学习、主动推送、定时任务、Telegram 交互、修改或删除原始记录、自动公开文章、多模型切换、插件市场、多 Agent、向量数据库。

知识范围仅为 Journal 已保存的条目和文章文本。照片、视频等条目已有的文字说明可以参与检索；附件本体、照片墙、游戏墙、留言、评论和站外内容不接入。未完成的条目草稿默认不作为知识来源。

站主登录后可查询自己的公开、私有和受保护记录。所有检索、正文与会话接口均沿用站主管理身份，不提供访客问答；访问 AI 入口时，未登录用户看到登录入口，登录完成后回到 AI 页面。

## 3. 页面与完整交互

沿用截图中的 AI 图标和位置，点击进入独立 `/ai` 页面；桌面与移动端入口一致。页面标题为“AI”，说明文案为“查找记录，连接想法”。

桌面保留网站导航，中间是对话，顶部提供“新对话”和“历史”按钮，底部固定输入框。历史按需展开，不新增常驻侧栏。来源直接放在回答下方，首版不做独立资料工作台。

移动端沿用“更多 → AI”，对话占满内容区域；历史以抽屉呈现。输入框随可视区域适配，避免被软键盘遮挡。

| 阶段 | 页面行为 |
| --- | --- |
| 首次进入 | 导航、标题和输入框立即出现，仅历史区域显示加载状态；空会话显示三个示例问题，点击只填入输入框 |
| 发送 | 用户消息立即出现在对话中，原位置显示“正在查找并整理”；同一会话本轮结束前不接受第二次发送，仍可编辑下一条输入 |
| 回答完成 | 原等待位置替换为回答与来源，不滚动重建整页；首版完整返回回答，不做逐字流式输出 |
| 阅读来源 | 点击引用展开已读取的正文片段；“打开原记录”进入现有管理详情，返回时恢复会话、输入草稿与滚动位置 |
| 连续追问 | 沿用当前话题及来源；改变主题时重新检索，不把旧来源硬套入新问题 |
| 切换会话或路由 | 已加载历史保留；进行中的请求归属原会话，返回内容不会插入新会话；切回不重复发起提问 |
| 刷新 | 从服务端恢复已保存消息；中断且没有完整回答的轮次明确显示未完成，不自动重发 |
| 保存整理稿 | 点击后按钮立即显示保存中；成功后变为“打开文章”，再次点击打开同一篇，不重复创建 |
| 取消离开编辑器 | 已保存文章仍为私有；回到 AI 时原会话与文章入口保留 |
| 请求出错 | 在当前轮次展示具体失败，保留用户输入和已完成消息；不自动重试、不切模型、不伪造答案 |

长对话阅读时保留用户当前滚动位置，新回答到达提供“查看新回答”入口。退出站主登录时清空前端私有会话缓存，后端访问继续受现有鉴权约束。

## 4. 回答规则

1. 涉及“我的记录”的事实必须先检索或读取原文，不能凭模型常识编造个人经历。
2. 检索结果摘要用于选资料，关键结论需要读取正文后再给出；引用只允许关联本轮实际读取或重新读取的来源。
3. 资料互相矛盾时列出各自时间和观点；模型提出的解释单独标注为推断。
4. 没找到时明确说“在本次检索范围内没有找到”，展示关键词与日期范围，允许用户补充线索。这是正常空结果，不等同于检索故障。
5. 只读到部分内容时写明“基于本次读取的 N 条记录”，不能宣称已经总结全部记录或完整的一周。
6. 引用标题、标识与跳转地址由服务端根据真实记录生成；原文中的命令只是待分析内容，不成为助手指令。

涉及站内资料的问题会将选中的正文发给当前模型服务。首版在输入框附近以简短说明交代这一数据使用范围，不把整个资料库或账号配置发送给模型。

## 5. 最小实现路径

### 5.1 模型与工具

继续使用 Journal 现有 DeepSeek 接入方式，沿用 `DEEPSEEK_TASK_MODELS.writing`，首版使用单一模型配置，关闭自动重试。新增 Journal 专用知识助手服务，不改 bot 的公共 AI 客户端。

模型仅获得两个只读业务工具：

| 工具 | 输入 | 输出 |
| --- | --- | --- |
| `search_entries` | 关键词组、可选标签、日期起止、分页位置 | 条目标识、标题、日期、匹配片段及是否还有结果 |
| `read_entries` | 条目标识和可选正文分段位置 | 标题、标签、正文片段、更新时间及正文是否完整 |

模型根据问题选择检索词并调用工具，服务端调用现有数据库能力，再将结果交还模型形成答案。工具调用能力有 DeepSeek 官方资料依据；具体参数仍须在实现时按所用接口核对。[DeepSeek Tool Calls](https://api-docs.deepseek.com/guides/tool_calls/)

不另建工具注册框架或任务调度系统。每个问题是一次前台请求内的有限查阅过程：建议最多四轮工具调用，每轮最多两个调用，最后一次只生成回答。额度结束即报告实际覆盖范围；工具或模型报错直接结束本轮，不继续生成假成功结果。

首版采用现有标题与正文关键词匹配，加上已有标签和时间条件。关键词组由模型一次提出，查询按词匹配并去重；标题、标签命中优先，时间作为次序依据。相关性排序和多关键词组合属于新增业务逻辑，不能把现有搜索直接称作语义检索。

建议每次检索返回十条候选、每次读取最多五条，正文分段返回并标明范围。单轮正文总量设显式上限，不能静默截断后假装读完。以上为首版工作量边界，不是对模型性能的测量结论。中文同义表达可能漏召回是这一选型的已知限制；出现真实高频漏查后再判断是否需要更换检索方式。

### 5.2 会话与上下文

会话保存在 Journal 现有 SQLite，新增两张业务表即可：

- 会话表：ID、标题、创建时间、更新时间。标题直接取首条提问的短文本，无需额外调用模型。
- 消息表：会话 ID、顺序、角色、内容、引用、完成或中断信息，以及整理稿已保存的文章 ID。

页面展示完整历史；模型上下文先使用最近十轮已完成问答和当前来源标识，并在界面说明上下文范围。历史回答不是当前事实依据，涉及原文事实的追问仍按需重新读取。若用户明确指向不在当前上下文中的旧消息，应让其选定对应内容，不猜测指代，也不建立自动摘要记忆系统。

模型工具过程中的临时材料无需全部长期保存。保留回答实际引用的片段和读取时的更新时间，历史来源预览注明“回答时引用”；打开原记录展示当前版本，来源删除时明确显示已删除。

### 5.3 整理与保存

“整理成文章”先在对话内生成可阅读的标题和正文，用户可继续要求缩短、重排或调整措辞。只有用户点击“保存为私有文章”才发生内容写入，模型没有直接发布权限。

保存接口根据已完成的消息创建文章，通过现有 `JournalArticleService.createArticle` 写入；标记 `aiGenerated: true`，默认不生成标签，随后在现有编辑器调整。

用现有 Markdown 与富文本能力转换整理稿，只支持现有编辑器能表达的基本标题、段落、列表和链接；不让模型自由拼装 Tiptap 内部结构。文章尾部保留参考来源，私有来源不会因保存或后续公开文章而改变自身权限。

保存结果与对应消息建立关联，文章创建和关联落库需在同一数据库事务中完成，避免响应丢失后重复保存。已关联的操作返回同一文章；关联文章已删除时直接说明事实，不自动补建。

当前文章创建行为是私有文章，方案不将它命名为数据库意义上的“草稿”，也不为了 AI 首版调整现有发布状态设计。

### 5.4 代码边界

| 区域 | 预计改动 |
| --- | --- |
| `web/src/components/ai/` | 新增对话页、消息与来源展示，复用现有导航图标 |
| `web/src/router.ts`、`web/src/app/`、`web/src/composables/useAppRoute.ts`、应用外壳 | 接入 AI 路由、站主访问和导航选中态；路由解析需同步接入，不能只增加路由表项 |
| `web/src/api/`、`web/src/stores/` | 会话请求和按会话存储的页面状态 |
| `src/journal-server/` | 知识助手服务、只读检索、会话存储、私有接口和现有迁移流程 |
| `src/shared/` | 提问、回答、来源与保存操作的数据协议 |
| `src/ai/models.ts` | 复用现有配置，本版无需改变模型名称 |

首版不新增运行时依赖、不新增服务、不跨服务器调用 bot。Journal 镜像已有 `src/journal-server`、`src/shared` 与 `src/ai/models.ts` 的复制路径，因此新服务优先留在这些范围内。

## 6. 实施顺序与首版完成标准

建议将以下内容作为同一批功能实现，完成后再进入发布决策：

1. 接通 AI 页面、站主身份、会话存储和两个只读工具，让一次真实问题产生带来源的回答。
2. 补齐连续追问、历史切换、来源阅读和页面状态复用，让用户可以持续使用。
3. 接入整理稿保存与现有文章编辑器，形成知识复用闭环。

首版完成标准按实际业务结果判断：

- 能根据一条自然语言问题找回站内真实记录，并从回答打开对应原文。
- 可以跨几条记录形成有依据的总结，追问仍能对应正确来源。
- 没有材料、材料不完整和调用出错时，页面明确区分这些结果。
- 刷新、查看原文再返回、切换会话，不丢失已保存问答，也不重复执行上一轮操作。
- 整理结果可保存为一篇私有文章并继续编辑，原始记录不被修改。
- 访客无法获取会话、私有来源或调用私人知识查询。

后续优先收集“经常找不到哪类内容”和“哪些整理结果会真正保存”这两类反馈，再决定是否扩展检索能力或内容范围。首版不先为设想中的未来需求增加基础设施。

## 7. 依据与确定程度

以下为本次阅读源码确认的事实，不作为线上运行效果的声明：

- `web/src/components/journal/PublicChannelNavigation.vue`：AI 点击会发出事件并显示开发中提示；`web/src/router.ts` 尚无 AI 页面。
- `src/journal-server/routes/privateEntries.ts` 与 `repository.ts`：已有站主鉴权、标题和正文匹配、标签及时间过滤；现有过滤对草稿的处理不能不加区分地直接沿用到 AI。
- `src/journal-server/articleService.ts`、`repository.ts` 与 `src/shared/journalProtocol.ts`：已有富文本文章创建和 AI 标记，文章创建明确设置为私有。
- `src/journal-server/aiSuggestionService.ts`：现有 Journal AI 负责主题和标签生成，通过 DeepSeek 调用，客户端设置 `maxRetries: 0`；这不是已有的 Agent 服务。
- `package.json` 声明 `openai: ^7.5.0`，本地包元数据为 `7.5.0`，对应源码类型包含聊天工具声明；仅据此确认本地 SDK 有相关接口表面，不推断远端调用结果。
- `src/journal-server/database.ts` 与 `deploy/journal/Dockerfile`：现有 SQLite、迁移入口和镜像复制范围可作为新功能落点。

检索效果、单次耗时、使用成本以及模型对真实问题的工具选择质量尚无本任务中的运行数据；本方案不承诺固定秒数、固定费用或完整召回率。文档中的页数、轮数及上下文范围均为建议的首版业务边界。
